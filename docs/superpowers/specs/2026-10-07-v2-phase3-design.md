# v2 Phase 3 — 에이전트별 권한 정책 설계 스펙

- 날짜: 2026-10-07
- 기준: main `a6368e3` (v2.0.0-beta.3)
- 브랜치: `feat/v2-phase3`
- 로드맵: `~/.claude/plans/mighty-floating-feigenbaum.md` 4장 Phase 3(R4)
- 앞 단계: `docs/superpowers/specs/2026-10-02-v2-phase2-design.md` (특히 13장 "실행 뒤 확인된 것과 남은 위험")

## 1. 목적

Phase 2까지의 대시보드는 Claude Code가 물어 온 것에 답만 했다. Phase 3부터는 **사용자가 에이전트마다 "이 도구는 쓰지 마", "이 도구는 쓸 때마다 물어봐"를 미리 정해 둘 수 있다.**

- 예: `reviewer`는 명령 실행과 파일 고치기를 못 하게 한다. `developer`의 명령 실행은 매번 묻게 한다.
- Claude Code에는 팀원마다 권한을 따로 정하는 기능이 없다. 그래서 `PreToolUse` hook으로만 강제할 수 있다.

### 사용자 결정 (2026-10-07)

| # | 결정 |
|---|---|
| D1 정책 범위 | **조이기만 한다.** 값은 `금지`와 `항상 질문` 둘뿐이다. 자동 허용은 넣지 않는다. 정책이 잘못되거나 악용돼도 최악의 결과는 "작업이 막힘"이다 |
| D2 정책 단위 | **에이전트 이름 기준이고 계속 적용한다.** 어느 세션에서든 이름이 같으면 같은 정책이다. 세션별 정책과 세션별 덮어쓰기는 넣지 않는다 |
| D3 도구 단위 | 도구 이름(묶음)으로만 가른다. 명령 내용이나 파일 경로로 가르는 규칙은 넣지 않는다 |
| D4 hook 인증 | 이번에도 넣지 않는다. 조이기만 하므로 가짜 hook으로 정책을 느슨하게 만들 수 없다. Phase 5 앞에서 다시 정한다 |
| D5 대시보드가 꺼져 있을 때 | 정책은 적용되지 않는다. 이 한계를 받아들이고 화면과 설명서에 분명히 적는다(8장) |

## 2. 전제와 확인 스파이크 (Task 0)

Phase 2는 스파이크가 "거부" 쪽만 확인해서, 끝에서 끝까지 확인 때에야 전제가 틀린 것이 드러났다. 이번에는 **쓰려는 모든 갈래를 구현 전에 실제 세션으로 확인한다.**

이미 확인된 것(Phase 0·2):
- `PreToolUse` hook은 즉시 응답해야 한다. 응답 형식은 `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"ask"|"deny","permissionDecisionReason":"…"}}`이다.
- 리드의 `PreToolUse`에 `ask`를 돌려주면 auto 모드에서도 권한 창이 뜬다(Phase 2 S4, 끝에서 끝까지 9번).
- 에이전트 식별은 `server/events/summarize.ts`의 `agentOf()`가 한다. `agent_id`가 없으면 리드, `a`+16진수면 리드에 합친 서브에이전트(`agent_type`이 종류), 그 밖은 팀원(`agent_type`이 이름)이다.

Task 0에서 확인할 것(실제 Claude Code 세션, 임시 폴더, 포트 4319 이상):

| # | 확인 | 틀리면 |
|---|---|---|
| S1 | 리드의 `PreToolUse`에 `deny`를 돌려주면 도구가 실행되지 않고, Claude가 `permissionDecisionReason`을 받는다. default 모드와 auto 모드 각각 | 범위를 줄인다: `deny`가 안 되면 `금지`를 빼고 `항상 질문`만 |
| S2 | **팀원**(in-process agent team)의 `PreToolUse`에 `deny`·`ask`가 적용된다. 팀원이 이유를 받고 턴을 이어 간다 | 팀원 정책을 범위에서 빼고 리드·서브에이전트만 |
| S3 | **서브에이전트**(Agent 도구로 띄운 `Explore` 등)의 `PreToolUse`에 `deny`·`ask`가 적용된다 | 서브에이전트 정책을 범위에서 뺀다 |
| S4 | 팀원·서브에이전트에 `ask`를 돌려줬을 때 권한 창이 **어디에** 뜨는지(리드 터미널인지), 그 `PermissionRequest`가 대시보드 큐에 오는지 | `항상 질문`을 리드에만 허용한다 |
| S5 | `deny`된 호출에 `PostToolUse`/`PermissionDenied` 등 어떤 이벤트가 뒤따르는지(Phase 2 큐·예산 관문과 섞이지 않는지) | 6.3의 순서 규칙을 고친다 |
| S6 | MCP 도구의 `tool_name` 모양(`mcp__서버__도구`)과, 도구 이름이 대소문자까지 고정인지 | 5.2의 묶음 정의를 고친다 |

스파이크 결과는 `docs/superpowers/spikes/2026-10-07-phase3-spike.md`에 적고, 틀린 전제가 있으면 위 표의 "틀리면" 대로 범위를 줄인 뒤 사용자에게 알린다. 스파이크 문서에는 실제 사용자 이름·경로를 적지 않는다.

안전 규칙은 Phase 2와 같다. 실제 claude는 절대 경로로, env는 명시해서, 사용자의 `settings.json`·설치본·4317 서버는 건드리지 않는다. 실험 세션은 팀이 멈출 때 함께 내린다(한도가 풀리면 스스로 재개한다).

## 3. 용어

- **대상**: 정책이 붙는 이름. 네 종류다.
  - `lead` — 리드(메인 세션)
  - `agent:<이름>` — 이름 있는 팀원(예: `agent:reviewer`)
  - `sub:<종류>` — 서브에이전트 종류(예: `sub:Explore`)
  - `others` — 위에서 정하지 않은 모든 팀원·서브에이전트
- **묶음**: 사용자가 고르는 도구 단위(5.2).
- **규칙**: (대상, 묶음) → `ask` 또는 `deny`. 규칙이 없으면 "기본"(Claude Code의 원래 규칙)이다.

## 4. 정책 모델

### 4.1 저장 형태

`<prefix>/policy.json` (설치본은 `~/.claude-office/policy.json`, 개발 모드는 `.logs/policy.json`).

```json
{
  "version": 1,
  "targets": {
    "lead": { "bash": "ask" },
    "agent:reviewer": { "bash": "deny", "edit": "deny" },
    "sub:Explore": { "edit": "deny" },
    "others": { "web": "ask" }
  }
}
```

- 값은 `"ask"` 또는 `"deny"`만 허용한다. 그 밖의 값(특히 `"allow"`)이 파일에 있으면 **그 규칙은 무시하고** 경고 로그를 남긴다(D1을 파일 조작으로 우회하지 못하게).
- 파일이 없거나 깨졌으면 빈 정책으로 시작하고 경고 로그를 남긴다. 깨진 파일은 덮어쓰기 전에 `policy.json.broken`으로 한 번 옮겨 둔다(정책은 사용자가 손으로 정한 것이라 잃으면 안 된다. 예산 상태와 다른 점이다).
- 쓰기는 예산 저장소와 같은 방식이다: 임시 파일을 0600으로 쓴 뒤 rename. 저장에 실패해도 던지지 않고, 메모리의 정책은 유지하며, API 응답으로 "저장 실패"를 알린다.
- 상한: 대상 200개, 대상 이름 100자(그래핌), 대상 이름에 제어 문자 금지. 넘으면 API가 400.
- `__proto__`·`constructor`·`prototype` 같은 키는 대상 이름·묶음 이름 어디에도 받지 않는다(Phase 2 Task 5 리뷰의 교훈). 내부 표는 `Map` 또는 null-prototype 객체를 쓴다.

### 4.2 판정 규칙

hook 입력 하나에 대해:

1. `agentOf(input)`으로 대상을 정한다.
   - 리드 → `lead`
   - 팀원 → `agent:<이름>`. 규칙이 하나도 없으면 `others`
   - 서브에이전트 → `sub:<종류>`. 규칙이 하나도 없거나 종류를 모르면 `others`
   - `agentOf`가 null이면 판정하지 않는다(빈 200).
2. `tool_name`으로 묶음을 정한다(5.2). 어느 묶음에도 안 들면 `other`.
3. 그 대상에 그 묶음의 규칙이 있으면 그것을 쓴다. 없으면 그 대상의 `all`(모든 도구) 규칙을 쓴다. 그것도 없으면 "기본"이다.

"대상에 규칙이 하나도 없을 때만 `others`를 본다"는 것이 중요하다. `agent:reviewer`에 `bash: deny`만 정했다면 reviewer의 웹 접근은 `others`의 `web: ask`를 **따르지 않는다.** 이름으로 정한 대상은 그 이름의 규칙만 따른다. 섞으면 "왜 이게 막히지"를 설명하기 어렵다.

### 4.3 판정은 동기, 메모리만

`PolicyGate.preToolUse(input)`은 메모리의 표만 보고 즉시 답하며 던지지 않는다. 파일 I/O는 하지 않는다. Phase 2의 예산 관문과 같은 계약이다(1초 안, 실측은 1ms 미만이어야 한다).

## 5. 도구

### 5.1 원칙

도구는 이름으로만 가른다(D3). `tool_input`은 보지 않는다. 그래서 정책 판정 경로는 명령 원문·파일 경로를 읽지도 보관하지도 않는다.

### 5.2 묶음

| 묶음 키 | 화면 이름 | `tool_name` |
|---|---|---|
| `bash` | 명령 실행 | `Bash` |
| `edit` | 파일 고치기 | `Edit`, `Write`, `NotebookEdit` |
| `web` | 웹 접근 | `WebFetch`, `WebSearch` |
| `agent` | 팀원·서브에이전트 만들기 | `Agent` (옛 이름 `Task`도 같은 묶음) |
| `mcp` | 외부 도구(MCP) | `mcp__`로 시작하는 모든 이름 |
| `other` | 그 밖의 도구 | 위에 없는 모든 이름 |
| `all` | 모든 도구 | (묶음별 규칙이 없을 때의 기본값) |

- 읽기 도구(`Read`, `Grep`, `Glob`)는 따로 묶지 않는다. `other`와 `all`에 들어간다.
- **답하기 도구와 팀 통신 도구는 정책에서 뺀다.** `AskUserQuestion`, `ExitPlanMode`, `SendMessage`, `TaskCreate`·`TaskUpdate`·`TaskList`·`TaskGet`에는 어떤 규칙도 적용하지 않는다(`all`과 `other`에도 들지 않는다). 사용자에게 묻는 길을 막으면 에이전트가 갇히고, `all: deny`를 건 팀원이 리드에게 "막혔다"고 보고조차 못 하면 조용히 멈춘 것처럼 보인다. 예외 목록은 묶음 정의와 같은 파일 한 곳에 둔다.
- 묶음 정의는 코드 한 곳(`server/policy/tools.ts`)에만 두고, 화면과 설명서는 테스트로 그 정의와 맞춘다.

### 5.3 바로 쓰는 묶음(템플릿)

화면에서 한 번에 채우는 조합이다. 저장되는 것은 결과 규칙뿐이고, 템플릿 이름은 저장하지 않는다.

| 이름 | 규칙 |
|---|---|
| 읽기 전용 | `bash: deny`, `edit: deny` |
| 명령은 물어보고 | `bash: ask` |
| 제한 없음 | 그 대상의 규칙을 모두 지움 |

## 6. 강제

### 6.1 응답

- `deny`: `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<이유>"}}`
  - 이유 문구(Claude가 읽는다): `대시보드 권한 정책: <대상 화면 이름>은(는) <묶음 화면 이름>을 쓸 수 없습니다. 다른 방법을 찾거나 사용자에게 알려 주세요.`
  - 이유에는 도구 입력을 넣지 않는다.
- `ask`: Phase 2의 `preToolAsk(reason)`를 그대로 쓴다. 이유 문구: `대시보드 권한 정책: <대상 화면 이름>의 <묶음 화면 이름>은 매번 확인합니다.`
- 응답 형식은 `server/decisions/protocol.ts` 한 곳에 두고 글자 그대로 테스트로 고정한다(기존 규칙).

### 6.2 판정 순서

같은 `PreToolUse`에 여러 판정이 걸릴 때:

1. 정책 `deny` → 즉시 deny. 예산 관문을 거치지 않는다(관문 기록도 만들지 않는다).
2. 예산 관문 → 걸리면 예산의 `ask`.
3. 정책 `ask` → 걸리면 정책의 `ask`.
4. 아무것도 아니면 빈 200.

예산이 정책 `ask`보다 앞인 이유: 둘 다 권한 창을 띄우는 것은 같지만, 예산 `ask`는 뒤따르는 `PermissionRequest`가 "예산 결정"으로 짝지어져야 한다(B48). 정책 `ask`가 먼저 답하면 예산에 닿은 호출이 일반 권한 요청으로 지나가 관문이 한 번 밀린다.

### 6.3 Phase 2 결정 큐와의 관계

- 정책 `ask`로 뜬 권한 창은 평범한 `PermissionRequest`로 온다. 큐는 그것을 `permission` 종류로 붙잡고, 대시보드에서 허용·거부할 수 있다. 큐 코드는 바꾸지 않는다.
- 보고서에 "왜 묻는지"를 한 줄 보여 준다: `권한 정책이 매번 확인하도록 정해 둔 도구입니다`. 정책 `ask`와 뒤따르는 `PermissionRequest`의 짝 찾기는 예산 관문과 같은 해시 방식(B48: 세션·도구 이름·입력 해시, 10초 안, 한 번만)을 쓴다. 해시만 보관하고 원문은 보관하지 않는다.
- 정책 `deny`는 큐에 아무것도 만들지 않는다(S5에서 뒤따르는 이벤트가 큐를 건드리지 않는지 확인).
- **대시보드에서 "허용"을 눌러도 정책은 바뀌지 않는다.** 그 한 번만 허용이다.

### 6.4 hook을 막지 않는다

정책 판정에서 예외가 나면 로그(오류 코드만)를 남기고 다음 단계로 넘어간다. 정책 오류가 도구 실행을 막거나, 예산 관문·큐의 동작을 막아서는 안 된다.

## 7. 화면

디자인은 designer가 Phase 1·2의 규칙(도트, 네온 팔레트, 쉬운 말, 색에만 의존하지 않기, `role="status"` 하나) 위에서 정한다. 이 장은 무엇이 있어야 하는지만 정한다.

### 7.1 에이전트 패널의 권한 칸

- 캐릭터를 누르면 지금은 결정이 있을 때만 보고서가 열린다. 결정이 없는 캐릭터를 누르면 **에이전트 패널**이 열린다(오른쪽 서랍, 보고서·진단 서랍과 서로 닫힘). 결정이 있는 캐릭터는 지금처럼 보고서가 먼저 열리고, 보고서 머리의 "권한" 버튼이나 정책 목록(7.2)으로 그 에이전트의 정책에 갈 수 있다.
- 패널 머리: 이름, 종류(리드/팀원/서브에이전트), "이 이름의 정책은 다른 세션의 같은 이름에도 적용됩니다" 한 줄.
- 권한 칸: 묶음마다 한 줄, 세 값 중 하나를 고른다 — `기본` / `항상 질문` / `금지`. 라디오 그룹이고 키보드로 고를 수 있다.
- 템플릿 버튼 세 개(5.3). 누르면 값이 채워지고, **[저장]을 눌러야 적용된다.**
- 서브에이전트는 리드 책상에 합쳐 그려지므로, 리드 패널 안에 "서브에이전트" 절을 두고 지금 보이는 종류와 "그 밖의 모든 팀원·서브에이전트"를 고를 수 있게 한다.
- 이 대상에 규칙이 없고 `others`를 따르는 중이면 그 사실을 보여 준다: `정한 것이 없어 "그 밖의 모든"을 따릅니다`.
- 저장 실패(400, 네트워크, 파일 저장 실패)는 패널을 닫지 않고 문구로 알린다.

### 7.2 정책 목록

- HUD에 "권한 정책" 버튼. 정책이 하나라도 있으면 개수를 보여 준다.
- 서랍: 저장된 모든 대상을 목록으로 보여 준다(지금 화면에 없는 이름 포함). 대상마다 요약(`명령 실행 금지 · 파일 고치기 금지`), [고치기], [지우기].
- [대상 추가]: 종류(팀원 이름 / 서브에이전트 종류)와 이름을 입력해 미리 정책을 만든다.
- 맨 위에 8장의 한계 한 줄을 늘 보여 준다: `대시보드가 켜져 있을 때만 적용됩니다.`

### 7.3 표시

- 규칙이 걸린 캐릭터에 자물쇠 표시. `aria-label`에 "권한 정책 있음"을 더한다.
- 정책이 막거나 물은 횟수를 패널에 보여 준다: `켠 뒤로 금지 3번 · 질문 5번`(서버 메모리 값이라 대시보드를 다시 켜면 0부터).
- 정책 `deny`가 일어나면 그 캐릭터의 말풍선에 한 줄: `정책으로 막힘: 명령 실행`. 손은 들지 않는다(사용자가 할 일이 없다).

### 7.4 스냅샷과 API

- 스냅샷의 각 member에 `policy?: { source: "own" | "others"; rules: Record<묶음, "ask"|"deny">; denied: number; asked: number }`를 싣는다. 규칙이 없으면 필드를 싣지 않는다.
- `GET /api/policy` — 전체 정책(인증 필요).
- `PUT /api/policy/targets/:target` — 한 대상의 규칙을 통째로 바꾼다. 본문 `{ "rules": { "bash": "deny" } }`. 빈 객체면 그 대상을 지운다.
- `DELETE /api/policy/targets/:target` — 지운다.
- 쓰기 API의 인증·같은 출처·JSON·크기 제한은 Phase 2의 `PUT /api/budget`과 같은 미들웨어를 쓴다. 모르는 키·모르는 묶음·`ask`/`deny` 아닌 값은 400.
- 정책이 바뀌면 `hub.poke()`로 스냅샷을 다시 만든다.

## 8. 한계 (화면과 설명서에 그대로 적는다)

1. **대시보드가 켜져 있을 때만 적용된다.** 서버가 꺼져 있거나 hook이 닿지 못하면 Claude Code는 원래 규칙대로 진행한다. HTTP hook의 동작이라 바꿀 수 없다. 이 기능은 "보안 장치"가 아니라 "실수 방지 장치"다.
2. **이름이 같으면 같은 정책이다.** 다른 프로젝트·다른 세션의 같은 이름에도 적용된다.
3. **도구 이름으로만 가른다.** `명령 실행`을 금지해도 `파일 고치기`가 열려 있으면 파일은 바뀐다. "읽기 전용" 템플릿이 둘을 함께 막는 이유다. MCP 도구로 같은 일을 할 수 있으면 그것도 따로 막아야 한다.
4. **이미 실행 중인 도구에는 소급하지 않는다.** 정책은 다음 도구 호출부터 적용된다.
5. **가짜 hook은 정책을 느슨하게 만들 수 없다.** 다만 Phase 2 스펙 13장의 한계(대기 상한 채우기 등)는 그대로다.
6. 플러그인이 설치되지 않았거나 회사 관리자 설정이 hook을 막으면 적용되지 않는다(doctor가 알려 준다).

## 9. 로그·진단·doctor

- 로그: 정책 판정 한 건에 `policy` 줄 하나. 내용은 결과(`deny`/`ask`), 묶음 키, 대상 **종류**(`lead`/`agent`/`sub`/`others`)뿐이다. 대상 이름과 도구 입력은 남기지 않는다(팀원 이름은 진단 번들에서 순번으로 가리는 대상이다).
- 진단 번들: 정책 통계(대상 수, 종류별 규칙 수, 결과별 판정 수). 대상 이름은 넣지 않는다.
- `qa:analyze`: "권한 정책" 절.
- doctor: 항목을 늘리지 않는다. 대신 정책이 하나라도 있는데 플러그인이 꺼져 있거나 hook 이벤트가 0건이면, 기존 `hooks` 항목의 안내에 `권한 정책이 적용되지 않고 있습니다` 한 문장을 더한다.
- 반복 억제: 같은 대상·묶음의 `deny`가 연달아 나오면 기존 로거의 반복 억제를 그대로 탄다.

## 10. 설치·제거·사용설명서

- 설치: `policy.json`은 만들지 않는다(처음 저장할 때 생긴다). 업그레이드 때 기존 `policy.json`은 그대로 둔다.
- 제거: `policy.json`과 `policy.json.broken`도 지운다. 제거 요약 문구는 그대로다("프로그램 파일"에 포함).
- 사용설명서(qa 작성, reviewer 검토, director 확인): 5장에 "권한 정책" 절, 6장에 증상 절("정책을 정했는데 안 막혀요", "에이전트가 갑자기 아무것도 못 해요"), 부록 A에 관리자용 사실(8장의 한계, 저장 위치, 로그에 남는 것).
- 설명서 그림은 designer가 그린다. 화면 문구·묶음 이름·이유 문구는 테스트로 코드와 글자까지 맞춘다(Phase 2 방식).

## 11. 완료 기준

1. **정책 모델** — 4장의 저장·판정 규칙이 테스트로 덮인다. 특히: `allow`가 파일에 있어도 무시, 깨진 파일은 `.broken`으로 보존, `__proto__` 계열 키 거부, "이름에 규칙이 있으면 `others`를 보지 않는다", 답하기·팀 통신 도구는 `all: deny`에서도 통과.
2. **강제** — `PreToolUse` 응답 형식 고정, 6.2의 순서(정책 deny → 예산 → 정책 ask), 정책 오류가 hook을 막지 않음, 판정 1ms 수준(실제 객체로 측정).
3. **화면** — 패널에서 고르고 저장, 목록에서 고치고 지우고 추가, 템플릿, 자물쇠 표시, 저장 실패 안내, 키보드 조작과 포커스 복귀, `role="status"` 하나 유지.
4. **누출 없음** — 로그·진단 번들·스냅샷에 도구 입력 원문, 토큰이 없다. 로그·진단 번들에 대상 이름이 없다.
5. **끝에서 끝까지(실제 세션)** — 최소 다음을 확인한다.
   - 팀원 하나에 "명령 실행 금지" → 그 팀원의 Bash만 막히고 이유를 받으며, 다른 팀원과 리드는 그대로다.
   - 리드에 "명령은 물어보고" → auto 모드에서도 권한 창이 뜨고, 대시보드 보고서로 허용할 수 있다.
   - 서브에이전트 종류에 "읽기 전용" → 그 종류의 Edit·Bash가 막힌다.
   - 예산 관문과 정책 `ask`가 같은 호출에 걸릴 때 예산 보고서가 뜬다.
   - 정책을 지우면 다음 호출부터 풀린다.
   - 대시보드를 끄면 정책이 적용되지 않는다(한계 1을 실제로 확인하고 설명서 문구와 대조).
6. **업그레이드 시나리오** — beta.3이 설치된 임시 HOME에서 새 버전을 설치한다. 플러그인 등록이 새 버전으로 바뀌고(FB-4), doctor가 전부 정상이며, 기존 `token`·`state.json`이 유지된다. 가짜 claude로 하되, 가짜 claude는 `plugin update` 호출을 기록한다.
7. 전체 테스트·typecheck·build·package 통과, 단독 최종 확인(새 worktree, `npm ci`, 전체 테스트 3회 실패 0), 원인 모르는 간헐 실패 없음.
8. 화면 배치는 jsdom 테스트로 못 잡는다(FB-6). designer가 구현 뒤 정적 렌더(`qlmanage`)로 패널·목록의 배치를 눈으로 확인한다.

## 12. 범위 밖

- 자동 허용(D1). 데이터 모델은 값 종류를 늘릴 수 있게 두지만, `allow`는 이번에 어떤 경로로도 받지 않는다.

- hook 요청 인증(D4).
- 정책 내보내기·가져오기, 회사 관리자가 배포하는 정책(Phase 5).
- 일시정지·종료·작업 지시(Phase 4).

## 13. 위험

- **스파이크에서 팀원·서브에이전트의 `deny`/`ask`가 기대와 다르게 동작할 수 있다.** 2장의 "틀리면" 열대로 범위를 줄인다. 가장 큰 불확실성은 S4(팀원의 `ask`가 어디에 뜨는가)다.
- **"보안 장치"로 오해될 수 있다.** 8장 한계 1을 정책 목록 맨 위와 설명서 첫 문단에 둔다.
- **`all: deny`로 에이전트를 가둘 수 있다.** 답하기·팀 통신 도구 예외(5.2)와 말풍선 표시(7.3)로 "왜 멈췄는지"가 보이게 한다.
- **이름 충돌.** 서로 다른 팀의 같은 이름이 같은 정책을 받는다(한계 2). 패널 머리에 늘 적는다.
- **hook 응답 형식은 연구 프리뷰다.** 형식은 `protocol.ts` 한 곳에 두고 테스트로 고정한다. 바뀌면 Task 0 스파이크를 다시 돌린다.
- **사용량 한도로 팀이 멈춘다**(Phase 2에서 두 번). 진행 기록에 멈춤을 적고, 실제 세션을 띄운 확인은 멈출 때 함께 내린다.

## 14. 실행 뒤 확인된 것과 남은 위험 (2026-10-07, 구현 `feat/v2-phase3`)

1–13장은 승인 당시 그대로 둔다. 구현하며 확인된 사실과 남은 위험을 여기에 적는다. 판정 원문은 진행 기록(`.superpowers/sdd/2026-10-07-v2-phase3/progress.md`)의 Ruling B74–B112에 있고, 계획 문서의 "실행 중 바뀐 것" 절에 모았다.

### 14.1 확인 스파이크 (2장, Ruling B94)
- S1~S6 전제가 **모두 맞았다. 범위는 줄지 않았다.**
  - 리드·팀원(in-process)·서브에이전트의 `PreToolUse`에 `deny`·`ask`가 적용된다.
  - `deny`된 호출은 실행되지 않고 이유를 받은 뒤 턴을 이어 간다.
  - 팀원·서브에이전트의 `ask` 권한 창은 **리드의 터미널**에 뜬다(창 머리에 `from the <이름> agent`).
  - 그 `PermissionRequest`에는 `agent_id`·`agent_type`이 있다.
  - `deny` 뒤에는 닫는 이벤트가 오지 않아 막힌 호출을 이벤트 저장소에 넣지 않는다(B79 확정).
  - MCP 도구 이름은 `mcp__<서버>__<도구>`이고 대소문자 그대로다.
- **빼는 도구가 여덟 개가 됐다.** 서브에이전트가 결과를 리드에게 돌려주는 `SubagentHandback`을 더했다. 막으면 서브에이전트가 갇힌다. `TaskStop`·`ToolSearch`는 빼지 않는다(그 밖의 도구).
- **Claude Code는 이유 앞에 `PreToolUse:<도구> hook error: `를 붙여 보여 줄 수 있다.** auto 세션에서 관찰됐다. 설명서에 "고장이 아니라 정책"이라고 적었다. 대시보드가 꺼졌을 때도 같은 앞말 뒤에 `connect ECONNREFUSED`가 붙으므로 둘을 구별하는 법도 적었다.
- 팀원을 별도 터미널 창(tmux·iTerm 분할)으로 띄우는 방식은 **확인 전**이다.

### 14.2 스펙과 달라진 점
- **이유 문구(B92, 6.1 대체):** 다음 두 문구를 쓴다. 따옴표 안은 **걸린 규칙**의 이름(B90: `all` 규칙으로 막히면 "모든 도구 금지")이고, 정책 목록의 요약과 같은 글자다.
  - deny `대시보드 권한 정책: <대상>에게는 "<묶음> 금지"가 정해져 있어 이 도구를 쓸 수 없습니다. 꼭 필요하면 사용자에게 알려 주세요.`
  - ask `대시보드 권한 정책: <대상>에게는 "<묶음> 항상 질문"이 정해져 있어 이 도구는 매번 확인합니다.`

  스펙 문구의 "다른 방법을 찾거나"는 우회를 권하는 것처럼 읽혀 뺐다.
- **패널 머리 문구(B93, 7.1):** `이 이름의 정책은…`은 팀원·서브에이전트에만 쓴다. 리드는 `리드의 정책은 모든 세션의 리드에 적용됩니다`, "그 밖의 모든"은 따로 정하지 않은 대상에 적용된다는 문구다.
- **정책 목록의 고정 두 행(B95, 7.2):** 리드와 "그 밖의 모든 팀원·서브에이전트" 행은 규칙이 없어도 늘 있다. 그래서 열린 세션이 없어도 두 대상을 정할 수 있다. 상한 초과는 `400 { "reason": "limit" }`다.
- **doctor 조건(B98, 9장):** 덧붙임 문장은 hooks 안내의 **앞**에 둔다. 조건은 "받은 이벤트 0건"과 "서버가 꺼져 확인하지 못함" 둘이다. "플러그인이 꺼져 있음"은 뺐다. plugin 항목이 `~/.claude/settings.json`만 봐서 다른 곳에서 켠 플러그인에 거짓 경고가 되기 때문이고, 정말 꺼졌으면 이벤트 0건이 잡는다.
- **빼는 도구 여덟 개(B94, 5.2):** 위 14.1.
- **`MultiEdit`는 `edit` 묶음(B86):** 옛 이름 `Task`가 `agent`에 드는 것과 같은 이유다.

### 14.3 스펙에 더한 것
- **읽지 못한 정책 파일 알림(B101~B104, B106):** 스펙 4.1은 경고 로그만 요구한다. 하지만 "정책을 걸었다고 믿는데 조용히 아무것도 적용되지 않는" 것이 이 기능의 가장 나쁜 실패라 화면과 doctor에 알린다.
  - 저장소 `unreadable()` → 스냅샷 `policy.unreadable`(불리언) → 정책 목록 맨 위 경고 + HUD 버튼 표시.
  - doctor "프로그램 파일" 항목은 warn이 된다.
  - 표시는 새 파일 쓰기에 성공해야 내려간다. 자동 복구·편집기는 없다.
- **방금 막힘 표시(B85·B93·B95·B108):** 정책 `deny` 뒤 30초 동안 표시한다. 서버가 3초 주기로 스냅샷을 다시 만들며 지난 것을 뺀다.
  - 자물쇠가 분홍이 되고 느낌표가 붙은 다른 모양이 된다(색에만 의존하지 않는다).
  - 책상 접근 이름에 `, 방금 정책으로 막힘`을 더한다.
  - 말풍선 첫 줄은 `정책으로 막힘: <묶음>`이다. 손은 들지 않는다.
- 저장하지 않고 떠나면 live region에 `저장하지 않은 변경을 버렸습니다`, 목록의 화면에 없는 이름에 `지금 없음`, 권한 칸 아래 빼는 도구 안내 한 줄(B93).

### 14.4 끝에서 끝까지 (11장 5, task-12, 실제 세션 프롬프트 7개 — B111)

2. 리드에 "명령은 물어보고": auto 모드에서도 권한 창이 떴다. 대시보드 보고서(`byPolicy`)로 허용해 실행됐다. ✅
3. 서브에이전트(Explore)에 "읽기 전용": Bash가 막혔다. ✅ **파일 고치기 금지는 실제 세션에서 확인하지 못했다.** Explore에는 Write·Edit 도구가 없다. 그래서 같은 서버에 보낸 가짜 PreToolUse(Explore, Write·Edit)로 서버 판정만 확인했다(판정은 도구 이름만 본다).
4. 예산 관문과 정책 `ask`가 같은 호출에 걸림: 예산 보고서가 떴고, 정책 ask 기록·횟수는 남지 않았다(B78). ✅
5. 정책을 지우면 다음 호출부터 풀렸다. ✅
6. 대시보드를 끄면 정책이 적용되지 않았다(한계 1). Claude Code 화면에 `hook error … ECONNREFUSED`가 보였다. 설명서에 반영했다. ✅

### 14.5 남은 위험
- **보고서의 "정책 때문" 이유 줄은 입력 해시가 맞을 때만 붙는다.** 정책 ask와 뒤따르는 PermissionRequest의 `tool_input` 해시가 같다고 실측된 도구는 Read·Write(이번 스파이크)와 Bash·Edit(Phase 2)뿐이다. WebFetch·MCP·NotebookEdit는 확인 전이다. 다르면 이유 줄만 빠지고, 권한 창과 정책 자체는 동작한다(설명서는 "보통"으로 적음, B110).
- **`agent_type`이 빈 PreToolUse는 정책 밖이다(B97).** `agentOf`가 null인 입력은 판정하지 않으므로 others의 규칙도 받지 않는다. 스파이크의 팀원·서브에이전트 PreToolUse에는 모두 있었다. 내부 보조 에이전트가 도구를 부르는 경우는 확인 전이다.
- **`TaskStop`은 빼지 않았다(B94).** 리드에 `all: deny`나 `other: deny`를 걸면 리드가 팀원 작업을 멈추지 못할 수 있다. 사용자가 터미널에서 멈추면 된다. 뺄지는 사용자 확인 항목이다.
- **대시보드가 켜져 있는 동안 `policy.json`을 손으로 고치면 반영되지 않는다.** 서버는 시작 때 한 번 읽고 그 뒤로는 메모리가 기준이라, 다음 화면 저장이 손 편집을 덮는다(B112, 설명서 부록 A에 "끈 뒤 고치기").
- **설치 스크립트·런처의 마지막 doctor는 기본 포트 4317을 조회한다.** 사용자 PC에서는 정상 동작이다. 개발 중 설치 테스트가 개발자의 대시보드를 보던 것은 테스트 래퍼로 막았다(B109). 제품 동작을 바꿀지는 사용자 확인 항목이다.
- Windows 실기, 별도 창 팀원, `allowManagedHooksOnly` 환경은 확인 전이다.
- Phase 2 13장의 가짜 hook 위험은 그대로다. 가짜 hook은 정책을 느슨하게 만들지 못한다(정책은 인증된 API로만 바뀌고, 판정은 막거나 묻게만 한다). 다만 아무 이름으로 "막힌 횟수"와 "방금 막힘" 표시를 만들어 낼 수 있다(상한 500, 표시만).
- 이름 충돌(한계 2)은 그대로다. 이름이 `team-lead`인 팀원은 화면에서 리드 책상에 합쳐지지만, 판정은 `agent:team-lead`로 따로 간다.
