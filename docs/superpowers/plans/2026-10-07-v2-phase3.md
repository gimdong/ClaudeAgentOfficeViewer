# v2 Phase 3 — 에이전트별 권한 정책 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 사용자가 에이전트 이름마다 도구 묶음을 `금지` 또는 `항상 질문`으로 미리 정해 두면, 대시보드가 `PreToolUse` hook으로 그 정책을 강제한다.

**Architecture:**
- **서버 정책:** `server/policy/tools.ts`(묶음 정의 한 곳), `server/policy/store.ts`(`policy.json`을 원자적으로 쓰고 깨진 파일은 `.broken`으로 보존), `server/policy/gate.ts`(메모리 표만 보는 동기 판정, 횟수, `ask` 짝 찾기).
- **hook 경로:** `/hooks/event`의 `PreToolUse`가 정책 `deny` → 예산 관문 → 정책 `ask` → 빈 200 순서로 답한다. 정책 `ask` 뒤의 `PermissionRequest`는 기존 결정 큐가 `permission`으로 붙잡고 "정책 때문"이라는 표시 하나만 싣는다.
- **API·스냅샷:** `GET /api/policy`, `PUT`·`DELETE /api/policy/targets/:target`(예산 API와 같은 인증). 스냅샷이 정책 전체와 구성원별 요약을 싣고, 화면은 스냅샷만 보고 그린다.
- **화면:** 캐릭터를 누르면 에이전트 패널(오른쪽 서랍), HUD의 "권한 정책" 버튼이 정책 목록 서랍을 연다. 서랍은 보고서·진단과 한 번에 하나만 열린다.
- **운영:** 로그는 결과·묶음·대상 종류만, 진단 파일은 통계만, doctor는 항목을 늘리지 않고 문장 하나를 더한다.

**Tech Stack:** Node 24 (ESM), TypeScript, Express 5, React 19, Vite, Vitest, jsdom, POSIX sh, PowerShell 5+

**Spec:** `docs/superpowers/specs/2026-10-07-v2-phase3-design.md` (커밋 69f96e2, 사용자 승인 2026-10-07)
**선행:** Phase 2 계획 `docs/superpowers/plans/2026-10-02-v2-phase2.md`("실행 중 바뀐 것" 절), Phase 2 스펙 13장, Phase 2 스파이크 `docs/superpowers/spikes/2026-10-02-phase2-spike.md`(실험 세션 띄우는 법), 디자인 `docs/design/phase1/SPEC.md` + `docs/design/phase2/SPEC.md` + `docs/design/phase3/SPEC.md`(Task 1), 팀 규칙 `.superpowers/sdd/2026-10-07-v2-phase3/team-protocol.md`

## Global Constraints

- 기준 브랜치 `feat/v2-phase3`(MERGE_BASE `a6368e3` = v2.0.0-beta.3, 스펙 `69f96e2`). push·merge·태그 push는 하지 않는다.
- Phase 1·2·베타의 제약은 그대로다: Node ≥ 24, `127.0.0.1`에만 바인딩, Host 검사, 서버는 claude home 아래에 아무것도 쓰지 않는다, UI 문구는 한국어, 이미지 파일을 쓰지 않는다, `role="status"`는 화면에 하나.
- **정책 값은 `"ask"`와 `"deny"` 둘뿐이다(D1).** `"allow"`는 파일·API·화면 어느 경로로도 받지 않는다. 파일에 있으면 그 규칙만 무시하고 경고 로그를 남긴다.
- **대상:** `lead`, `agent:<이름>`, `sub:<종류>`, `others`. 이름 있는 대상에 규칙이 **하나라도** 있으면 `others`를 보지 않는다(스펙 4.2). `lead`는 `others`를 따르지 않는다.
- **묶음 키:** `bash`, `edit`, `web`, `agent`, `mcp`, `other`, `all`. 정의는 `server/policy/tools.ts` 한 곳에만 둔다. 판정은 `tool_name`만 보고 `tool_input`은 읽지 않는다(D3).
- **정책에서 빼는 도구(어떤 규칙도 적용하지 않는다):** `AskUserQuestion`, `ExitPlanMode`, `SendMessage`, `TaskCreate`, `TaskUpdate`, `TaskList`, `TaskGet`.
- **판정 순서(스펙 6.2):** 정책 `deny` → 예산 관문 → 정책 `ask` → 빈 200. 정책 `deny`는 관문 기록도 큐 항목도 만들지 않는다.
- `PolicyGate.preToolUse`는 메모리 값만 보는 동기 함수이고 던지지 않는다. 정책 쪽 예외는 오류 코드만 로그에 남기고 다음 단계(예산 관문)로 넘어간다. `/hooks/event`는 어떤 경우에도 hook을 막지 않는다.
- hook 응답 형식은 `server/decisions/protocol.ts` 한 곳에만 두고 글자 그대로 테스트로 고정한다.
  - `deny`: `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<이유>"}}`
  - `ask`: 기존 `preToolAsk(reason)` 그대로.
- **문구(스펙 그대로. 조사는 Ruling B76):**
  - deny 이유: `대시보드 권한 정책: <대상 화면 이름>은(는) <묶음 화면 이름 + 을/를> 쓸 수 없습니다. 다른 방법을 찾거나 사용자에게 알려 주세요.`
  - ask 이유: `대시보드 권한 정책: <대상 화면 이름>의 <묶음 화면 이름 + 은/는> 매번 확인합니다.`
  - 보고서 이유 줄: `권한 정책이 매번 확인하도록 정해 둔 도구입니다`
  - 값 이름: `기본` / `항상 질문` / `금지`. 템플릿: `읽기 전용` / `명령은 물어보고` / `제한 없음`.
  - 묶음 화면 이름: `명령 실행`, `파일 고치기`, `웹 접근`, `팀원·서브에이전트 만들기`, `외부 도구(MCP)`, `그 밖의 도구`, `모든 도구`.
  - 패널 머리: `이 이름의 정책은 다른 세션의 같은 이름에도 적용됩니다`. `others`를 따를 때: `정한 것이 없어 "그 밖의 모든"을 따릅니다`.
  - 목록 맨 위: `대시보드가 켜져 있을 때만 적용됩니다.` 요약 예: `명령 실행 금지 · 파일 고치기 금지`.
  - 횟수: `켠 뒤로 금지 3번 · 질문 5번`. 말풍선: `정책으로 막힘: 명령 실행`. 자물쇠 `aria-label` 덧붙임: `권한 정책 있음`.
  - doctor 덧붙임 문장: `권한 정책이 적용되지 않고 있습니다`
  - 스펙에 없는 나머지 문구는 `docs/design/phase3/SPEC.md`의 문구표가 기준이고, **코드에 넣기 전에 qa가 앞뒤 출력과 나란히 읽어 검토한다**(팀 규칙 9).
- **상한:** 대상 200개, 대상 이름 100자(그래핌), 제어 문자 금지. `__proto__`·`constructor`·`prototype`은 대상 이름·묶음 이름 어디에도 받지 않는다. 넘으면 API는 400. 내부 표는 `Map` 또는 null-prototype 객체.
- **누출 금지:** 로그·진단 파일·스냅샷에 도구 입력 원문과 토큰이 없다. 로그·진단 파일에는 **대상 이름도 없다**(결과, 묶음 키, 대상 종류 `lead`/`agent`/`sub`/`others`, 숫자만). 스냅샷에는 대상 이름이 있어도 된다(화면이 그려야 한다).
- 정책 파일: 설치본 `<prefix>/policy.json`, 개발 `.logs/policy.json`. 임시 파일(0600) → rename. 설치는 이 파일을 만들지 않고, 업그레이드는 그대로 두며, 제거는 `policy.json`과 `policy.json.broken`을 지운다(제거 요약 문구는 그대로).

## Review Focus

1. **패널에서 값을 고르는 중에 스냅샷이 다시 오는 경우(3초마다 온다):** 사용자가 고르던 값이 서버 값으로 되돌아가면 안 된다. 편집 값은 패널을 열 때 한 번만 서버 값으로 채우고, 그 뒤로는 사용자가 바꾼 것을 지킨다. → Task 7 테스트 `편집 중에 스냅샷이 다시 와도 고른 값이 그대로다`
2. **값을 바꾸고 [저장]을 누르지 않은 채 닫는 경우:** "금지를 걸었다"고 믿고 넘어가면 실수 방지 장치가 거꾸로 실수를 만든다. 저장하지 않은 변경이 있으면 저장 버튼 옆에 그 사실을 보여 주고, 저장 전에는 요청을 보내지 않는다. → Task 7 테스트 `바꾼 값이 있으면 저장하지 않았다고 알리고, 저장 전에는 PUT이 없다`
3. **대상 이름에 `/`, `%`, 공백, 한글, 콜론이 있거나 주소의 퍼센트 인코딩이 깨진 경우:** 저장한 이름과 지우는 이름이 같아야 하고, 깨진 주소는 스택이 아니라 400이어야 한다. → Task 5 테스트 `이름에 슬래시·한글·콜론·퍼센트가 있어도 PUT·GET·DELETE가 같은 대상을 가리킨다`, `퍼센트 인코딩이 깨진 주소는 400`
4. **가짜 hook이 에이전트 이름을 바꿔 가며 쏟아지는 경우:** 횟수·"방금 막힘"·`ask` 짝 찾기 기록이 끝없이 늘면 서버 메모리와 스냅샷이 커진다. 각각 상한(대상 키 500개, 세션당 호출 20건)을 두고 오래된 것부터 버린다. → Task 4 테스트 `이름을 바꿔 가며 10,000번 막혀도 횟수 표는 500개를 넘지 않는다`
5. **`policy.json`을 손으로 고친 경우(값이 `"Deny"`, `targets`가 배열, 앞에 BOM, 숫자 값, 모르는 `version`):** 서버는 켜져야 하고, 읽을 수 있는 규칙만 살리며, 통째로 못 읽는 파일은 다음 저장 전에 `.broken`으로 옮겨 잃지 않는다. → Task 3 테스트 `손으로 고친 파일의 이상한 모양들`

## 계획서 판정 (계획을 쓰며 정한 것, B74부터)

- **Ruling B74 (버전):** 개발 버전을 `2.2.0-dev`로 올린다(Task 2). — 스펙 11장 6번의 업그레이드 시나리오는 "beta.3 → 새 버전"이라 버전이 달라야 플러그인 등록이 바뀌었는지 볼 수 있다. — 틀리면 비용: 배포 버전 번호는 어차피 최종 보고에서 사용자가 정한다(Phase 2와 같음).
- **Ruling B75 (hook 입력에서 대상 정하기):** `agentOf(input)`이 null이면 판정하지 않는다. 합쳐진 서브에이전트면 `sub:<agent_type>`(종류를 모르면 `others`), `agent_id`가 없으면 `lead`, 그 밖은 `agent:<이름>`이다. 이름이 대상 이름 규칙(100자, 제어 문자, 예약어)에 안 맞는 팀원은 자기 규칙을 가질 수 없으므로 `others`로 본다. 화면의 구성원은 `role === "lead"`면 `lead`, 아니면 `agent:<name>`이다. — 이름이 "team-lead"인 팀원과 리드를 `agent_id` 유무로 가른다. — 틀리면 비용: 한 함수(`agentKeyOf`).
- **Ruling B76 (이유 문구의 조사와 대상 화면 이름):** 스펙 6.1의 틀은 `<묶음>을`, `<묶음>은`으로 적혀 있지만 "파일 고치기을"은 틀린 말이다. 묶음마다 조사를 붙인 꼴(`obj`: "명령 실행을"·"파일 고치기를", `topic`: "명령 실행은"·"파일 고치기는")을 `tools.ts`에 함께 둔다. 대상 화면 이름은 리드 `리드`, 팀원은 이름 그대로, 서브에이전트 `서브에이전트(<종류>)`(종류를 모르면 `서브에이전트`)이고 이유 문구에서는 100자(그래핌)로 자른다. 규칙이 `others`에서 왔어도 이유에는 **그 에이전트 자신의 이름**을 쓴다(읽는 쪽이 그 에이전트다). qa가 Task 4 전에 일곱 묶음 × 두 문구를 읽어 확인한다. — 틀리면 비용: Claude와 설명서에 문법이 틀린 문장이 나간다.
- **Ruling B77 (화면은 스냅샷만 본다):** 스냅샷에 `policy: { targets, counts }`(정책 전체와 횟수)를 싣고, 패널·목록은 그것으로 그린다. `GET /api/policy`는 스펙대로 두되 화면은 쓰지 않는다(CLI·확인용). — 저장 뒤나 다른 탭에서 바꾼 뒤 화면이 낡은 값을 들고 있는 상태를 없앤다(Phase 2 B58 계열). — 틀리면 비용: 대상이 200개면 스냅샷이 십수 KB 커진다.
